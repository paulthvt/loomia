# Calendar Versioning Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Releases are versioned `YYYY.MM.MICRO` (`2026.10.1`) and cut by yeet instead of release-please. The build, Play internal, web preview and promote flow stay as they are (#306).

**Architecture:** `.yeet.yaml` configures one CalVer target. It writes `pubspec.yaml` and `CHANGELOG.md` in a Release PR, and tags and publishes the GitHub release once the PR is merged. In `release.yaml`, the `release-please` job becomes `yeet`. That job diffs the CalVer tags before and after `yeet release` to find the new tag and passes it to `artifacts`, which checks it out and builds as today. The build number keeps its formula, now read as year/month/micro.

**Tech Stack:** GitHub Actions, yeet v0.17.1 (Docker image pinned by digest), GitHub App token, Dart (`tool/release_notes.dart`).

**Spec:** `docs/superpowers/specs/2026-10-13-calver-design.md`. No Figma: no UI.

## Global Constraints

- No new Dart dependency and no migration. Stage only changed files by path. The working tree has unrelated changes (`pubspec.lock`, `.kiro/`, `devtools_options.yaml`, `supabase/snippets/`) that stay out.
- Actions pinned by full SHA with a `# vN` comment; the yeet image by `tag@sha256:digest`:
  `docker://ghcr.io/monkescience/yeet:v0.17.1@sha256:f017d78597e31fb28eb17b46f46e5a18590b7d8f8e68ed194776800b41cf1be8`.
- CalVer tag regex, the same everywhere: `^v[0-9]{4}\.[0-9]{1,2}\.[0-9]+$`.
- Quality gate per task: `dart format .`, `flutter analyze` ("No issues found!"), `flutter test`. For workflow files, also `actionlint` if installed (`brew install actionlint`), otherwise read the YAML back.
- Branch `chore/306-calver`; PR title `chore: release with CalVer and yeet`; body `Closes #306`.
- Nothing is pushed to the remote (tags, secrets, the App) by the agent. Task 5 is the maintainer's.

## Rulings made while planning

- **The new tag is found by diffing tags, not by `git tag --points-at HEAD`.** yeet skips a run when a newer push is waiting, and the newer run tags the earlier merge commit, so `HEAD` can be past the tag. Diffing also means a re-run with nothing new builds nothing.
- **`artifacts` checks out the tag.** It used to build `github.sha`, which is the release commit only when nothing lands right after it.
- **No `--build-name`.** At the tag, `pubspec.yaml` already holds the version yeet wrote, which is what release-please did too.
- **The `yeet` job's own permissions are `contents: read`.** Writes go through the App token. The top-level `pull-requests: write` goes; `artifacts` keeps `contents: write` for `gh release`.
- **Tags are `vYYYY.MM.MICRO`** (found while implementing): yeet rejects an empty `tag_prefix`. The version itself, in `pubspec.yaml` and the PR title, has no `v`.
- **The bootstrap tag `v2026.10.0` was pushed during Task 2** (found while implementing): yeet lists tags through the GitHub API, so a local-only tag is invisible to the dry run. No workflow triggers on tags.
- **No `safe.directory` step for the Docker action.** yeet reads git through go-git, which has no ownership check.
- **The `release_notes.dart` regex for links is unchanged.** yeet's `([abc1234](url))` already matches it.
- **`DO_NOT_TRACK=1` on the step as well as `telemetry.enabled: false`.** If `.yeet.yaml` is invalid, yeet ignores the file, and so ignores the opt-out in it; the env var still applies.

- [x] **Step 2: Permissions and job.** The top-level `permissions:` becomes `contents: read` only. Replace the `release-please` job with:

  ```yaml
    yeet:
      runs-on: ubuntu-latest
      permissions:
        contents: read
      outputs:
        tag: ${{ steps.tag.outputs.tag }}
      steps:
        # yeet needs the full history and tags.
        - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7
          with:
            fetch-depth: 0

        - name: CalVer tags before
          run: git tag -l | grep -E '^v[0-9]{4}\.[0-9]{1,2}\.[0-9]+$' | sort > "$RUNNER_TEMP/before" || true

        # yeet force-pushes its release branch; an App token also gets CI to run
        # on the Release PR. Setup: README.md → Releases.
        - uses: actions/create-github-app-token@bcd2ba49218906704ab6c1aa796996da409d3eb1 # v3
          id: app
          with:
            client-id: ${{ vars.YEET_APP_ID }}
            private-key: ${{ secrets.YEET_APP_PRIVATE_KEY }}

        - uses: docker://ghcr.io/monkescience/yeet:v0.17.1@sha256:f017d78597e31fb28eb17b46f46e5a18590b7d8f8e68ed194776800b41cf1be8
          with:
            args: release
          env:
            GITHUB_TOKEN: ${{ steps.app.outputs.token }}
            DO_NOT_TRACK: '1'

        # yeet has no outputs. Not --points-at HEAD: when a push follows the
        # merge, yeet tags the merge commit from the newer run.
        - name: Tag created by this run
          id: tag
          run: |
            git fetch --tags --force --quiet
            git tag -l | grep -E '^v[0-9]{4}\.[0-9]{1,2}\.[0-9]+$' | sort > "$RUNNER_TEMP/after" || true
            echo "tag=$(comm -13 "$RUNNER_TEMP/before" "$RUNNER_TEMP/after" | tail -1)" >> "$GITHUB_OUTPUT"
  ```

- [x] **Step 3: `artifacts`.**
  - `needs: yeet` and `if: needs.yeet.outputs.tag != ''`.
  - Its checkout gets `with: ref: ${{ needs.yeet.outputs.tag }}`.
  - Every `needs.release-please.outputs.tag_name` (six of them) becomes `needs.yeet.outputs.tag`.
  - The versionCode step becomes:

    ```yaml
          # Play needs a strictly increasing versionCode, iOS a CFBundleVersion: the
          # same number, derived from the tag so promote.yaml can find the build.
          # ponytail: 100 releases a month at most (micro < 100).
          - name: Compute versionCode
            id: version
            env:
              TAG: ${{ needs.yeet.outputs.tag }}
            run: |
              IFS=. read -r year month micro <<< "${TAG#v}"
              echo "code=$((year * 10000 + month * 100 + micro))" >> "$GITHUB_OUTPUT"
    ```

  - Checked locally: one CalVer tag in `before`, two in `after`, and `comm -13` prints only the new one. With equal lists it prints nothing. `IFS=. read` of `2026.10.1` gives `20261001`.
