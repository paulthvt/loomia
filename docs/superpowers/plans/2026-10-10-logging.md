# Logging Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Unexpected failures reach Sentry with their stack trace, and every Sentry event shows the routes, Supabase requests and user id that came before it. Expected failures leave a breadcrumb, and being offline reports nothing. Debug builds print every log record to the console (#265).

**Architecture:** `package:logging` is the only logging API. `sentry_logging` turns records into breadcrumbs (`INFO`+), structured logs (`WARNING`+) and events (`SEVERE`). The two guards (`guardPeople`, a new top-level `guardAuth`) choose the level; the mapping functions stay pure. `main.dart` holds all the wiring.

**Tech Stack:** Flutter (`material_ui`), `flutter_riverpod` 3, `go_router` 18, `supabase_flutter` 2.17, `sentry_flutter` 9.30.1, `logging` 1.3, `sentry_logging` 9.30.1.

**Spec:** `docs/superpowers/specs/2026-10-10-logging-design.md`. No Figma (no UI).

## Global Constraints

- **Dart imports:** `package:loomia/...`; Material from `package:material_ui/material_ui.dart`.
- **Dependencies:** each one gets a pubspec comment giving its reason. `sentry_logging` is pinned to exactly the `sentry_flutter` version (`9.30.1`, no caret), with a comment saying they move together.
- **PII:** no names, emails, phones, notes or titles in log messages. Ids, codes and counts only.
- **Quality gate per task:** `dart format .`, `flutter analyze` ("No issues found!"), `flutter test`. No goldens change.
- **Branch:** `chore/265-logging` off `main`. The PR body says `Closes #265`. Stage changed files by path; leave the user's untracked files (`.kiro/skills/`, `devtools_options.yaml`, `supabase/snippets/`) and the `pubspec.lock` drift alone unless Task 1 changes the lockfile.

## Rulings made while planning

- **`guardAuth` becomes top-level** in `auth_failure_mapping.dart`. `AuthRepository._guard` needs a `SupabaseClient` to test; a free function taking a closure doesn't, the same as `guardPeople`. `AuthRepository` calls it in place of `_guard`.
- **Loggers are top-level `final _log = Logger('<area>');`** in the file that logs: `people` in `people_repository.dart`, `auth` in `auth_failure_mapping.dart`, `photos` in `photo_repository.dart`, `router` in `app_router.dart`.
- **`guardPeople` doesn't log a `PeopleFailure` it catches.** It was already handled where it was raised (the repository threw it on purpose).
- **The `PostgrestException` sent to Sentry is a copy** with `message` and `code` only; `details` and `hint` are dropped (they can hold row values).
- **Router breadcrumb:** `router.routerDelegate.addListener` reading `router.routerDelegate.currentConfiguration.uri.path`. `router.dispose` (already in `ref.onDispose`) disposes the delegate and its listeners, so there's nothing to remove. Not unit-tested: one line, checked in Task 5.
- **`discard` isn't unit-tested** (see the spec's Testing section). The existing `if` stays; only the call inside it changes.
- **`Supabase.initialize(debug: false)`** (found while running Task 4). Supabase prints its own `Logger('supabase')` records in debug, and without hierarchical logging every logger shares the root stream, so each line printed twice. Its records still reach the root listener.
- **Console format:** `'${r.level.name} ${r.loggerName}: ${r.message}'`, then `r.error` and `r.stackTrace` on their own lines when present. `debugPrint`, not `print` (it throttles, and the lint rejects `print`).

## Review Focus

1. A bug reaches Sentry as an event with its real stack; a refusal and a network error don't. Pinned by the guard tests in Tasks 2 and 3.
2. Nothing personal leaves the device: `details` is dropped (Task 2 test), query strings are dropped (`beforeBreadcrumb`, checked in Task 5), the user is id-only.
3. Debug builds still send nothing to Sentry (empty DSN unchanged).

    Logger.root.onRecord.listen((r) {
      debugPrint('${r.level.name} ${r.loggerName}: ${r.message}');

      if (r.stackTrace != null) debugPrint('${r.stackTrace}');

      .listen(
        (state) => Sentry.configureScope(

### Task 2: `guardPeople` logs

**Files:**
- Modify: `lib/features/contacts/data/people_repository.dart`
- Test: `test/features/contacts/data/people_repository_test.dart`

- [x] **Step 1: Failing tests,** in a `group('guardPeople logs', ...)`. Collect `Logger('people').onRecord` into a list (`Logger.root.level = Level.ALL` in `setUp`, cancel the subscription in `tearDown`). Each test awaits `expectLater(guardPeople(() async => throw X), throwsA(<failure>))`, then checks the records:
  - `SocketException('offline')` → one `INFO`, no `SEVERE`.
  - `PostgrestException(message: 'm', code: '23505', details: 'Key (email)=(a@b)')` → one `SEVERE`, message `23505: m`, `error` is a `PostgrestException` with `details == null`, `stackTrace` not null.
  - `TypeError()` (throw it via `(null as dynamic).x`, or `throw TypeError()`) → `SEVERE` with a stack trace.
  - `PeopleFailure.network` → no records.
- [x] **Step 2: Implement.** `catch (error, stack)`, then:
  ```dart
  final failure = peopleFailureFrom(error);
  switch (error) {
    PeopleFailure() => null,
    _ when failure == PeopleFailure.network => _log.info('offline', error),
    final PostgrestException e => _log.severe(
      '${e.code}: ${e.message}',
      PostgrestException(message: e.message, code: e.code),
      stack,
    ),
    _ => _log.severe('unexpected', error, stack),
  };
  throw failure;
  ```
  (Write it as an `if` chain if the switch statement reads worse after `dart format`.)
- [x] **Step 3:** Quality gate.
